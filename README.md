### ⚠️ 财务是【累计】口径 —— 两个聚宽接口口径相反

这条踩过坑，实测结论：

| 接口 | 口径 | 证据 |
|---|---|---|
| `finance.STK_INCOME_STATEMENT`（pitdb 用的） | **累计**（年初至今） | 平安银行 2017 归母净利 Q1 6.21e9 → H1 1.26e10 → Q3 1.92e10 → 年报 2.32e10，四期全和 ≈ 2.6× 年报 |
| `get_fundamentals(statDate=...)` | **单季** | 平安银行 2017 四个单季 `net_profit` 相加 == 年报，精确相等 |
| `get_history_fundamentals(interval='1q'/'1y')` | **单季** | 000800 营收 2018Q1 7.15e9 > Q2 6.33e9 > Q3 5.55e9（累计不可能递减）；300028 的 2016-12-31 营收 = −2.91e5（累计年营收不可能为负） |

⚠️ `interval='1y'` **不是「年报」**，是「每年同一报告期的单季值」——
`watch_date=2018-12-28, count=7` 给的 `statDate` 是 2012-09-30…2018-09-30，
锚在最新可用报告（2018Q3）上。按「累计+年报」理解会让所有因子口径反推全部失败。
详见 [docs/jqfactor-口径.md](docs/jqfactor-口径.md)。

**用错就全废。** 累计口径下：

```
TTM(t) = 累计(t) + 上年年报 − 上年同期累计       （年报本身即 TTM）
同比    = 累计(t) / 上年同期累计 − 1              （直接可比，无需 TTM）
```

TTM 自洽性已断言：年报当期 `np_ttm == net_profit_parent`（违反 0）。
600519 实测：2023 年报累计 747.34 亿 = TTM 747.34 亿；2024Q1 累计 240.65 亿 → TTM 780.04 亿。

### 单季：raw 存累计、std 存单季，分层各司其职

```
单季(t) = 累计(t) − 累计(同年上一期)        （Q1 的单季 == 累计）
单季同比 = 单季(t) / 上年同期单季 − 1        （比累计同比更敏感）
```

**分层原则**：`raw` 只存累计（保真、可从源重建）；`std/fin_quarterly.parquet`
落单季（好用）；面板同时提供累计/TTM/同比/单季。
不是同一层放两份冗余字段，而是各层职责不同。

**交叉验证通过**：平安银行 2017 从累计减出 **62.140 / 63.400 / 65.990 / 40.360 亿**，
与 `get_fundamentals` 直接给的单季**精确一致**。

⚠️ **连续性必须比季度序号，不能用日期减法** ——
`2017-06-30` 减 3 个月 = `2017-03-30`，与 `2017-03-31` 对不上，会误判不连续
（这个 bug 让可算率从 98.06% 假跌到 74.01%）。

覆盖率：**98.06%** 的报告期可算单季（267,730/273,018）。不可算的是
「年内首期不是 Q1」5,075 期 + 「报告期跳跃（Q1→Q3 等）」213 期 → 置 NULL（`q_ok=false`）。

**有了单季就能在本地复现 FROEC 的原公式** `4×最新单季ROE − Σ前四季ROE`
（那个公式本来就是单季口径的）。实测复现后立刻暴露一个问题：
`increase` 读数高达 **2938** —— 净资产接近零的股票让分母爆掉。
原公式没有 winsorize，会被极端值主导。这是之前只能靠回测猜、现在本地一眼可见的。

🔴 **`roe_parent` / `eps_basic` 等累计比率跨报告期不可横截面比较** ——
Q1 的 ROE 天然只有年报的 1/4。**选股请用 `roe_ttm`**。
（这正是小市值那条线上踩过的坑：因子在 4 月披露期附近会因报告期错配而失真。）

### 估值：自算的比买来的更严格

`pb / pe_ttm / ps_ttm / roe_ttm` 的分母全部取**当日可见**的财报（`fin_visible_at` 语义），
而现成的 `pb_ratio` / 因子库用的是「当前最新财报」，本身可能含未来数据。
**这不是妥协，是升级。**

实测（2024-06-28 贵州茅台）：pb 7.69 / pe_ttm 23.63 / ps_ttm 11.69 / **roe_ttm 32.54%** /
营收同比 18.04% / 净利同比 15.73% / peg 1.50 —— 与真实估值吻合。

全市场分位（2010 年后）：pb 中位 **2.79**、pe_ttm 中位 **37.6**、roe_ttm 中位 **6.20%**。
`pe_ttm` 空值多于 `pb`（亏损股 `np_ttm <= 0` 时为 NULL，这是正确行为）。

### 涨跌停价：规则 + 自校验闭环

**`is_open_limit_up` 就是「开盘即封、买不进」的判据** —— 小市值线卡了很久的那个缺口。

| 板块 | 条件 | 幅度 |
|---|---|---|
| 科创板 `sh68*` | 2019-07-22 开板即 | ±20% |
| 创业板 `sz30*` | `date >= 2020-08-24`（注册制，ST 亦 20%） | ±20% |
| 创业板 `sz30*` | ST | ±5% |
| 创业板 `sz30*` | 其余 | ±10% |
| 主板 | ST 且 `date >= 2026-07-06` | **±10%** |
| 主板 | ST | ±5% |
| 主板 | 其余 | ±10% |

价格 `round(preclose*(1±pct), 2)`。**前提已验证**：`preclose` 在除权日已是除权后价格
（600519 在 2024-06-19：1521.500 − 30.8760 = 1490.624，精确吻合）。

#### 🔴 2026-07-06 那条规则是从数据反推的，不是查规则查到的

| 区间 | 5% 规则越界 | 10% 规则越界 |
|---|---|---|
| 2026-01-01 ~ 07-03 | **0.018%**（3/16,934） | — |
| 2026-07-06 起 | **13.801%**（732/5,304） | **0.000%** |

证据极强（10% 规则零越界，且 2026-07 月内可见 0.05→0.10 的切换），
**但具体监管依据未核实**。若发现有误，改 `ST_MAIN_10PCT_FROM` 常量即可。

#### `limit_rule_ok` —— 用数据兜底，不枚举新股规则

新股上市前几日无涨跌幅限制（创业板/科创板前 5 日、主板 2023-04-10 后前 5 日），
历次规则变更繁多且易错。做法是：**当日实际 `high`/`low` 越界即 `limit_rule_ok=false`**，
四个 `is_*` 标记也随之为 false，因此不会产生假的涨停标记。

实测 `limit_rule_ok` 占比 **99.9725%** —— 不可信的 0.03% 几乎全是新股无限制期。

### 停牌：为什么是单独一张表

`mart/paused_daily` = 交易日历里有、面板里无 = **全天停牌**。

停牌的票**本来就没有行**，列放不进面板。分工是：
- **选股**：面板已天然正确（停牌票不在里面，选不到）
- **持仓**：查这张表（手里的票停牌了卖不出）

停牌峰值精确命中 2015 股灾：**2015-07-09（1,442 只）/ 07-10（1,386）/ 07-08（1,316）**。

只覆盖全天停牌。盘中临时停牌（有成交、只交易半天）日线上看不出来，不在此表 ——
那种情况实盘仍能买卖，对选股无影响。

`fin_report_date` / `fin_pub_date` 是**可审计性**列 —— 随时能查「这一行用的是哪期财报、哪天公告的」。没有它面板就是黑盒。

### as-of 语义（每一处都显式，少一个就是未来函数）

| 项 | 做法 |
|---|---|
| 财务 | `ASOF on pub_date`，且先剔除「旧报告期的事后重述」（按 pub_date 取 running max(report_date)，只留 report_date=max 的行） |
| 行业 | 区间 join `[valid_from, valid_to)` |
| ST | `ASOF on GREATEST(valid_from, known_from)` —— 状态须**已生效**且**已知道**，取晚的那个 |
| 成分 | 季度快照（88 个）。**快照日的选择必须全局**：先 ASOF 出当日适用的 `as_of`，再按 `(code, as_of)` 精确 join |
| 上市 | `list_date` 静态，算 `listed_days` |

⚠️ **成分那条踩过坑**：若按 code 各自 ASOF，退出成分的票会一直保留最后一次「是成分」的状态（只进不出）—— 实测让沪深300 变成 316 只、中证1000 变成 2097 只。改成全局快照日后精确为 300 / 500 / 800 / 100 / 50。

### 构建时的 21 项断言（`--verify`）

全部通过。其中三条是 PIT 核心：

- `fin_pub_date <= date` —— 无未来财务（违反 0）
- `listed_days >= 0` —— 无上市前行情，走**白名单**而非放宽阈值
- 主键 `(date, jq_code)` 唯一

### 三层判据

| 层 | 判据 | 可否重建 |
|---|---|---|
| **raw** | 能从数据源原样重跑得到 | ✅ 重跑采集 |
| **std** | 需要跨源决策 或 需要历史版本 | ✅ 从 raw 重算 |
| **mart** | 供消费者直接使用的成品 | ✅ 从 std 重算 |

**核心不变量：std / mart 全部可从 raw 重算。只有 raw 需要备份。**

### `_ingest/` 是什么

每个源的采集工具、上游缓存、中间库都放在自己源目录下的 `_ingest/`：
- 下划线前缀 → 排序在数据目录前，一眼看到边界
- 备份/gitignore 可按 `_ingest/` 统一匹配（代码进 git，`tdx.db` 与 `downloads/` 不进）

**为什么 `tdx.db` 在 `_ingest/` 而不算 raw 数据**：它是采集工具的工作库，
每日增量导入、会被覆盖写，且 `slim_tdx_db.py` 之类的操作会改 schema。
`raw/tdx/kline/` 存的是从它导出的**按年冻结**的 parquet —— 冻结才有 PIT 意义。
约定：**只重新导出当年分区，往年一律冻结。**

## 🔑 三大报表 / 业绩预告的增量语义（2026-09-01 定案）

**三大报表走【整年重抽、整文件替换】，不做行级合并。**
`extract_jq_financials.py` 本来就按 `report_date` 年份分片存
`income_YYYY.csv.gz` 等，而 `load_jq_financials.py` glob 全部年份文件重建
parquet —— 所以换掉当年那几个文件、重跑 loader 就是完整刷新。没有合并，
就没有「缺列 / 类型错位 / 去重键选错」那一类风险。

抽取侧两个必须一致的点（不一致**不会报错**）：
- 源必须是 `finance.STK_INCOME_STATEMENT` 等，**不是**
  `get_fundamentals(query(income))` —— 两者 schema 不同
- 必须带 `report_type == 0`（只要合并报表）—— 漏掉会把母公司报表一起拉进来，
  行数翻倍、两种口径混在一张表里

替换侧的护栏：**新文件行数 < 旧的 95% 直接拒绝**。整年重抽本该 >= 旧的
（重述只会增行），缩水多半是抽取中断或配额耗尽给出的"看着正常的小文件"。

**业绩预告的 CSV 是上游写坏的**，必须用 `build/csv_repair.py` 读 ——
细节与三个解析器的分歧见 `docs/数据字典/4-按陷阱索引.md` B 节。

### 为什么财报和 30 年日线一个量级

**不是行多，恰恰相反 —— 财报行数只有日线的 3.5%：**

| | 行数 | 列数 | 单元格 | 体积 | 压缩比 |
|---|---|---|---|---|---|
| 日线 30 年 | 3,128 万 | 8 | 2.50 亿 | 513 MB | **1.61x** |
| 财报 4 张表 | 109 万 | 340 | 9,295 万 | 245 MB | **1.15x** |

两个原因，第二个是主因：

1. **列宽 15~40 倍**：日线 8 列（OHLCV + 额），资产负债表 **126 列**、
   现金流 92、利润 69、指标 53。
2. 🔴 **压不动**：资产负债表里 **111 个 DOUBLE 列占 98% 体积，压缩比只有
   1.08x**（8.3 字节/值，约等于原样存）。看值就明白：

   ```
   total_assets = 9473215236.16      ← 12 位有效数字 + 角分
   小数位分布：两位（角分）261,455 行 / 整数（元）12,079 行
   ```

   **带角分的 12 位金额把 DOUBLE 的 53 位尾数用满，是纯高熵数据** ——
   ZSTD 无从下手，dictionary 编码也没有重复值可用。
   而日线是 `11.21` 这种小范围价格 + 整数成交量，且按 (symbol, date) 排好序，
   delta + dictionary 都有效。

   **本质：财报存的是"会计精度的大额金额"，日线存的是"两位小数的价格"。
   同一个 8 字节的格子，前者塞满了信息，后者只塞了一点点。**

★ 试过一个**无损**的省法：改用「分」存 BIGINT（`947321523616`）——
273,534 行还原回元逐行一致，**但只省 16%**（全表约 39 MB）。
为这点收益改 loader、把 raw 从"原样保真"变成"带单位约定"，不值得。
（有损的那版 —— 直接 `CAST AS BIGINT` 丢角分 —— 省 34%，但 96% 的行会变值，
与"raw 保真"直接冲突，不做。）

★ **这 245 MB 不是回测的成本**，是档案费。下游早就裁过了：

```
raw/jq/financials/balance.parquet   126 列  91 MB   ← 原始档案
std/fin_quarterly.parquet            15 列  18 MB   ← 下游真正用的
```

回测吃 `mart/panel_daily`，根本不碰那 126 列。留着全宽是为了"以后想用哪一列
都还在"，而重抽一次聚宽的成本（配额 + 时间）远高于 245 MB 磁盘。

重复约 1.6 GB，两处都必要：
- **tdx.db** 是采集工作库（增量导入 + 复权重算），而 parquet 是为 PIT **冻结**
  的副本 —— 不冻结就会被每日覆盖静默改变
- **downloads/ CSV 不是 parquet 的副本，而是超集**（见下方发现）

## 🔴 已知缺陷：财报重述被压平，信息滞后中位数 47 天

`raw/jq/_ingest/downloads/indicator_*.csv.gz` 有 **340,690 行**，
`raw/jq/financials/indicator.parquet` 只有 **275,000 行**。差异不是格式，是**丢了版本**。

同一 `(code, end_date)` 会被多次公告 —— 业绩快报先出、定期报告后出：

```
300089.XSHE 2019 年报（CSV 里的 5 条 / 2 个公告日）
  2020-02-28  业绩快报   本年净利 -172,861,018.88     ← 当时能看到
  2020-05-29  定期报告   本年净利 -172,461,018.88     ← 修正后
parquet 只保留了 2020-05-29 那版
```

全局：29,074 组多版本中 **26,568 组（91.4%）保留了最晚版本**，早期版本被丢弃。
其中 **22,665 组**早晚公告日相差 >30 天，**中位数 47 天**。

实测后果：

```sql
-- 现实：2020-02-28 已发业绩快报，2020-03-15 当天能看到 2019 年度数字
SELECT * FROM fin_visible_at(DATE '2020-03-15') WHERE code='300089.XSHE'
-- 实际返回 2019Q3（公告 2019-10-30），不是 2019 年报
```

**性质判定**：
- ✅ **不是未来函数** —— 没有泄漏未来信息，方向是保守的
- ⚠️ **是信息滞后** —— 低估当时可用信息，平均 47 天

**影响面**：
- 季度频率的基本面选股（小市值/红利）：影响有限
- **事件驱动策略（业绩快报超预期、预增预减）：致命** —— 信号价值全在那 47 天里

**可修，且不用重新采集**（CSV 保留了完整多版本）：
1. 重跑 `build/load_jq_financials.py`，dedup 规则从「取最晚 `pub_date`」改为
   「保留所有不同 `pub_date` 的版本」（同 pub_date 的完全重复行仍要去掉）
2. `fin_visible_at` 的窗口排序改为 `ORDER BY report_date DESC, pub_date DESC`
   —— 同一报告期取「当时最新的那一版」

## 成交量单位陷阱与分层职责（2026-08-26）

通达信原始 `volume` 字段的值是**股数 × 100** —— 既不是「股」也不是「手」
（若是手，股数应为 `volume × 100`）。

**验证**（2026-08-24）：

| 标的 | 收盘 | 原始 volume | volume/100 | amount/close 推算 |
|---|---|---|---|---|
| 贵州茅台 sh600519 | 1304.66 | 484,395,700 | **4,843,957 股** | 4,828,000 |
| 平安银行 sz000001 | 11.56 | 11,990,249,500 | **119,902,495 股** | 119,669,000 |

两个口径差 0.3% 以内（分母用收盘价而非均价）。另有独立交叉验证：
`volume/100` 算出的换手率 0.4731 与面板 `turnover` 列 0.473107 精确吻合，
而 `turnover` 来自 tdx 的另一张表。

最可能成因：采集侧对一个本已是「股」的字段又做了一次「手 → 股」的 ×100 转换。
链路 `.day 文件 → Go 采集器 → tdx.db.raw_kline_daily → raw/tdx/kline/*.parquet`
全程未做单位换算，即原始字段本身如此。

### 分层职责

| 层 | 做法 |
|---|---|
| **raw** | 按采集原样保存，`volume` 保持原值 —— 可追溯性由这一层承担 |
| **mart** | **只暴露正确的列**：`volume_shares`（股数）。不重复保留错误列 |

清洗层再带一份错误列就违背了分层的意义。
改名而非只加注释，遵循 `build_canonical_views.py` 已有的原则
「把语义写进列名，让人不必记住这些坑」—— 旧查询用 `volume` 会**直接报错**，
而不是静默算错 100 倍。

### 四个类别的单位是统一的（已核对）

| 类别 | 验证方式 | 结果 |
|---|---|---|
| stock | `volume/100` 算换手率 vs 面板 `turnover` | 0.4731 vs 0.473107 ✓ |
| etf | `amount/(volume/100)` vs 收盘价 | 比值 0.9999 ✓ |
| index | volume 与成分股加总对比 | 上证综指 3.152e12 vs sh6* 加总 3.149e12（差 0.1%）✓ |
| block | 同 index | 隐含平均股价合理 ✓ |

⚠️ **我第一次核对 index/block 的方法是错的** —— 拿 `amount/(volume/100)` 去比
「收盘价」，而指数的收盘价是**点位**不是股价，比值当然不等于 1，于是误判成
「口径不同」。正确的检验是与**成分股加总**对比，以及看隐含平均股价是否落在
合理区间（上证 10.59 元 / 沪深300 15.96 元 / 中证500 11.09 元）。

指数只被 `assay` 的 `feed.benchmark()` 用来取 `close`，不涉及 volume，所以无需改动；
但单位统一这件事记在这里，避免以后有人拿指数 volume 直接用。

## ★ 面板构建的确定性（2026-08-26 修）

**同一份源数据三次重建，下游回测年化得到 41.31% / 40.73% / 42.52% —— 跨度 1.8pp。**

### 根因：ASOF JOIN 右表键不唯一

| 表 | `(code, pub_date)` 重复行 | 占比 |
|---|---|---|
| fin_quarterly | 23,444 | 8.617% |
| fin_indicator_q | 23,484 | 8.775% |
| security_status | 3 | 0.025% |

**补披露 / 延迟披露**会在同一天公布多个报告期：`000338` 在 2007-06-28 一天披露
6 个报告期，`300201` 在 2022-12-13 披露 Q1/Q2/Q3。键并列时 ASOF 取哪一行不确定；
而剔除事后重述用的窗口 `ORDER BY pub_date` 在并列时行序任意，运行中最大值也跟着变。

### 修法与不变量

`_fin` / `_ind` / `_status` 三处 ASOF 右表先按键去重（同日多期取**最新那期**）。

> **不变量：ASOF JOIN 的右表键必须唯一。** 新增 ASOF join 时必须先确认这一点，
> 否则整个构建变成不确定的 —— 而不确定的构建会让每一次对比都带上不可归因的误差。

副作用（**负向，2026-08-27 已修**）：`std/fin_quarterly.parquet` 由本脚本顺带写出，
当时也随之变为键唯一 —— 而这正是问题所在。

> ### ⚠️ 那次去重丢了三分之一的年报
>
> A 股公司常在 4 月**同一天**披露年报和一季报。L0 里 24,032 个 `(code, pub_date)`
> 同日多期分组中 **97.4% 含年报**，主形态 `[3,12]` 有 **23,398 组**。
> 「同日多期取最新那期」= 留一季报、**丢年报**。
>
> 而 `np_ttm` 的公式是「本期累计 + **上年年报** − 上年同期累计」，级联后果：
>
> | 环节 | 修复前 | 修复后 |
> |---|---|---|
> | `fin_quarterly` 年报行数 | 45,271 | **68,969** |
> | 有 Q3 却缺年报 | 23,229 (34.6%) | **266 (0.4%)** |
> | 上年年报缺失行的 `np_ttm` NULL 率 | 100.0% | — |
> | 面板 `np_ttm` NULL (2025) | 48.97% | **1.94%** |
> | 面板 `pe_ttm` NULL (2025) | 60.74% | **29.5%** |
>
> （`pe_ttm` 仍有约 29% NULL 是**正确的** —— 亏损公司 `np_ttm ≤ 0`，负 PE 对
> `BETWEEN 5 AND 50` 这类过滤没有意义。）
>
> **为什么没被发现**：`pe_ttm BETWEEN 5 AND 50` 遇 NULL 得 NULL → 行被丢，
> 不报错、不告警、结果看着完全合理。用 JQ 2019 `valuation` 对拍才暴露：
> JQ 每期都比本地多选 2~3 只，9 个 JQ 独有的入选票里 6 个正是 `np_ttm=NULL`。
>
> **修法**：把两个目标拆开 ——
> · 推导链（`_fin`）**完整保留全部报告期**，不去重、不做单调过滤；
> · ASOF 右表另建 `_fin3_asof`，只在那里按 `(code, pub_date)` 取最新报告期。
>
> **因此 `std/fin_quarterly.parquet` 现在【不再是键唯一】**：`(code, pub_date)`
> 会有重复（年报+一季报同日）。消费方做 as-of 必须自行按 `(code, pub_date)`
> 取最新 `report_date`，不能假设唯一。
`std/fin_indicator_q.parquet` 由 `load_jq_indicator_q.py` 产出，仍保留真实的同日多期重复。

### 校验失败不再静默放行

面板是**先写盘、后校验**的，失败时坏数据已在磁盘上。现在除 `sys.exit(1)` 外
还会落 `mart/panel_daily/_FAILED`，下游（assay 的 PanelFeed）直接拒绝加载。
主键重复时打印重复行明细而不只是计数。

## 决定：股本数据保持 tdx 现有行为（2026-08-26）

`std/share_change.parquet`（`finance.STK_CAPITAL_CHANGE`，236,709 行 / 5,600 只 /
1991-2026）已入库，但**不接进 panel** —— 它的角色是**裁判与参照**，不是数据源。

### 为什么不用它修正 tdx

实测 tdx 的流通股本已经 **98.39%** 符合权威表（流通A股口径），
剩余 **1.1%（117,536 行 / 1,912 只）**不符，本可修正。**但代价不成比例**：

权威表的 `change_date` 是**变动生效日**，`pub_date` 是**公告日**，
**生效到公告中位 50 天**。按 `change_date` as-of 的话，
**39.05% 的命中行其变动当日还没公告** —— 等于让回测提前知道未公告的股本。

| 方案 | 收益 | 代价 |
|---|---|---|
| 按 `change_date` as-of | 修正 1.1% | 39% 的行引入「已生效未公告」信息 |
| 按 `greatest(change_date, pub_date)` | 修正部分 | 比 tdx 现状**更滞后** |
| **保持 tdx 现状** | — | 保留 1.1% 偏差 |

tdx 现有行为介于两者之间（宁波银行案例：2019-06-30 生效、08-30 公告，
tdx 从 **7 月**起采用）—— 比 `change_date` 保守、比 `pub_date` 及时。

**1.1% 的精度换不来 39% 的 PIT 妥协。用户决定：不改。**

### 这张表仍然保留，因为它是唯一的独立裁判

它已经推翻了三个我先前基于「权威源更准」的假设：

| 字段 | 我的假设 | 裁判结果 |
|---|---|---|
| `valuation.pb_ratio` | 权威源更准 | 含 **6.58% 前视**，本地 PIT 正确 |
| `valuation.capitalization` | 权威源更准 | 与会计报表不符，**tdx 正确**（70.6% / 98.41% 两个裁判） |
| `valuation.circulating_cap` | 3.75% 分歧是口径差 | 不是口径差，**tdx 胜率 91.9%** |

以后再遇到「本地 vs 某个权威源」的分歧，先用它裁判，不要默认本地是错的一方。

单位备忘：`share_total` / `share_rmb` / `share_trade_total` 都是**万股**
（与 `balance.paidin_capital` 对拍 98.41% 吻合）。
表是**混合语义**：56.6% 的行 `change_reason='定期报告'`（报告期快照），
其余是真实事件（限售股份上市 / 可转债转股 / 股份回购 / 转增 / 增发 / 激励解禁）。

### ⚠️ 副作用：数据指纹的一个误报

`assay` 的数据指纹按 `std/*.parquet` 这个 glob 算聚合哈希，
所以**新增这个文件会让 `std` 部件的哈希变化**（12 → 13 个文件），
即使 panel 完全没读它。已归档的回测再 diff 会显示「数据版本不同」。

这是**误报而非漏报**（指纹的设计方向就是宁可误报），
`n_files` 从 12 变 13 也能提示「是新增文件而非内容变更」。
但要知道这一点，别把它当成 panel 数据真的变了。

### ★★ 源数据里有裸 `\r`，会【静默】多读行

聚宽 `STK_LIMITED_SHARES_LIST` 的 `shareholder_name` 里嵌了**孤立回车符**
（不是 `\r\n`），例如 `长沙中\r南升华\r科技发\r展有限\r公司`。

`to_csv` 的 QUOTE_MINIMAL 只对含分隔符/引号/`\n` 的字段加引号，**不管裸 `\r`**，
于是一条逻辑行被写成多行。危险在于**不报错**：

| 年 | 抽取时写入 | 直接读到 | 该年裸 `\r` 个数 |
|---|---|---|---|
| 2009 | 2,619 | 2,630 | **11** ✓ 精确匹配 |
| 2015 | 4,246 | 4,251 | 5 |

DuckDB 的 `read_csv_auto` 在 9/20 个文件上**直接探测失败**（反倒是好事，它拒绝了）；
只有 `strict_mode=false` 能读 —— 但那会把拆开的行当独立行，**行数错了却不报错**。

**处理**：加载器先按字节 `re.sub(rb'\r(?!\n)', b'', raw)` 清掉裸 `\r`
（不动 `\r\n`），再解析，并**逐年断言行数与抽取时一致**，对不上就 `exit(1)`。
共清掉 34 个。

> **不变量：从外部 CSV 加载时必须有行数断言。** 「能跑但数据错了」是最贵的失败模式。

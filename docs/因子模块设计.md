## 一、判据（用项目自己的，不新发明）

| # | 判据 | 出处 |
|---|---|---|
| ① | 依赖方向**单向** `assay → datalake`，反向零依赖 | 实测：`grep -rl "import assay" datalake --include='*.py'` **0 个文件** |
| ② | 按**产品域**拆，不按技术分层 | `srv/` `lv/` `stk/` `views/` `tests/` 五次拆分的同一判据 |
| ③ | **一件事只许有一份实现** | `symbols.py` / `paths.py` / `yiv` / `pnlv` 四个正本那一轮 |
| ④ | **feed 管「从哪取、as-of 怎么算」，策略管「阈值、分位、排序、截断」** | `feed.py:340` 的注释原文 |
| ⑤ | 「理想中**只有 feed 知道 datalake 的存在**」 | CLAUDE.md「策略数据 API」那节 |
| ⑥ | 不该进日频回测链的东西**顶层独立目录**，构建链一个脚本都不碰 | `datalake/rt/`（分钟线） |
| ⑦ | 链尾那一步失败**不影响主面板** | `sync_daily.sh` 的 9/9 |

### 🔴 反例就在 datalake 里：`build/backtest_froec.py`

477 行、一个完整的本地回测，而 `assay/README.md:895` 自己写着

## 二、结论：**拆成两半，都不建第三个仓库**

「量化因子模块」其实是两件事，边界正好落在判据 ④ 那条线上：

| 层 | 回答什么 | 放哪 | 为什么 |
|---|---|---|---|
| **因子值** | 「这只票今天 MA20 是多少」 | **datalake** | 它是**数据的派生量**：只吃面板、与策略无关。与 `build_beta_daily.py`（滚动回归 β）、`build_jqfactor_q.py`（TTM 同比）**同类** |
| **因子取数 API** | 「把 2018-06-01 这批因子给我」 | **assay `feed` + `guard`** | 判据 ④⑤：第四个取数 API，与 `universe` / `snapshot` / `fundamentals` 并列 |
| **因子评价** | 「**这个因子好不好**」 | **assay** | 要 forward return + 分组 + 调仓假设 = **回测语义**；产品域上与「★ 选中的规则」「策略比对」同一块（做策略时才进的） |

### 为什么因子值归 datalake 而不是 assay

先例是**既成事实**，不是类比：

```
datalake/build/build_beta_daily.py   滚动 252 日回归 β        -> std/beta_daily.parquet
datalake/build/build_jqfactor_q.py   TTM 与同比成长 13 列      -> std/jqfactor_q.parquet
```

这两个脚本做的事与「算 MA20 / ROE_TTM」**是同一类**：读面板、做窗口/as-of 运算、
落一份派生表。它们的 docstring 还把该说的都说了 ——
`build_beta_daily.py`：「beta **不是专有因子**，它就是个股日收益对基准日收益的
回归系数」「⚠️ 定义未与聚宽对标，故把三个自由度都做成显式参数」；
`build_jqfactor_q.py`：「🔴 `sg_approx`/`eg_approx` 是【近似】不是复现」。

**把因子值放 assay 的代价是可预见的**：同一个 MA20 会在回测取数与看盘页各算一遍
（判据 ③），而 `assay/stock.py` 那次「`_alt_map` 与 `symbols._kind_map` 是**逐字
相同的两份**」就是这么来的。

### 为什么因子评价归 assay 而不是 datalake

它需要三样 datalake 没有、也不该有的东西：

    forward return   「买了之后 20 天涨多少」—— 那是交易假设，不是数据
    分组与调仓        十分位等权组合 = 一个 mini 回测
    结论的归宿        picks / 归档 / 「★ 选中的规则」那套决策证据都在 assay

而按判据 ② 看更直接：**因子评价与"做策略"是同一个产品域**，
`backtest_froec.py` 的教训就是把这个域的东西放错了仓库。

### 为什么不建第三个仓库

| | |
|---|---|
| 会造出**三角依赖** | 新仓库依赖 datalake、又被 assay 依赖，而 assay 本来就依赖 datalake |
| 纪律是**按仓库**组织的 | CLAUDE.md / selftest / 数据字典 / picks / 归档 —— 第三个仓库要么复制一套（判据 ③ 当场破），要么一样都没有 |
| 收益不存在 | 独立发布、多人协作、独立 CI —— 本项目一条都用不上 |

## 三、落点

### 3.1 datalake 侧

```
datalake/build/factors/
  __init__.py     Spec + FACTORS 注册表 + Ctx（共享窗口算子，带缓存）
  expr.py         🔴 表达式求值器 —— 试跑与落盘**共用这一份**
  ma.py    18     均线 / 趋势        osc.py   27  摆动 / 超买超卖
  vol.py   22     量能 / 资金流      turn.py  13  换手率
  dist.py  10     收益分布 / 波动    pos.py    8  价格位置 / 回归
  （待建）fin_ratio.py / fin_ttm.py  会计比率 / TTM —— 要 as-of，第三期
  tools/check_vs_indicators.py   与 assay/indicators.py 逐值对数（25 项）
datalake/build/factor_try.py           试：公式 -> 全历史体检 / --as-spec / --dups
datalake/build/build_factor_daily.py   落：按股票分块建面板
datalake/build/build_factor_catalog.py 目录表（从注册表生成）
datalake/mart/factor_daily/            产物，按年分区
```

★ **按因子族分文件，不按「SQL 层 / pandas 层 / numba 层」分** —— 后者是技术分层，
  与判据 ② 背道而驰，而且改一个因子要跳三个文件。

⚠ **没有 `recur.py`**（初版设计里有）。当初的理由是"递推的实现手段就是那一族的
  定义特征"，实际做下来递推只落成 `Ctx.ema` / `Ctx.wilder` **两个算子**，
  而 MACD / TRIX / ATR 各自归在语义所属的族里更自然 —— 按实现手段单开一个
  文件那一步，其实就是技术分层。记在这里免得下次当成"漏了"。
⚠ 也**没有用 numba**：初版引的那个「numba 0.37s vs 纯 Python 40.19s」是上一轮
  原型的数。实际实现里递推走 pandas 的 `ewm`（带 SMA 起步），
  滚动窗口走 numpy 的 `sliding_window_view` —— 98 个因子全市场 3 年 35.5 秒，
  已经不是瓶颈，不必引一个新依赖。

### 3.2 `Spec` —— 一个因子一条声明（照 `assay/indicators.py` 的形状）

```python
Spec(
    id      = 'ma20',
    group   = 'ma',                     # 因子族（= 文件名）
    label   = '20 日均线',
    formula = 'MA(C, 20)',              # 怎么算的（进广场、进接口）
    desc    = '价格的 20 日算术平均',    # 干什么用的
    unit    = '元',                     # 🔴 比率一律标 '小数(0.05=5%)'
    deps    = ('close_hfq',),           # 依赖哪些面板列 -> 增量时只读这些
    warm    = 20,                       # 预热几根（下限见下）
    tier    = 'std',                    # ✅✅exact / ✅std / ⚠️own  见 3.3
    sparse  = None,                     # 非 None 时页面与评价表必须显示这句话
    persist = True,                     # 落不落 mart（见 3.5）
    calc    = _ma20,                    # (df, p) -> Series
)
```

🔴 **加一个因子只改一处**，接口 / 评价 / 页面自动就有 —— 这条是
`assay/indicators.py` 那一轮的直接套用：

> 改造前 MACD/KDJ 的公式写死在三处，加一个指标要改三处，
> **而漏掉画的那处不报错** —— 只是选中它之后副图一片空白

★ **判据取注册表，不写死清单**（同「`/api/sector/kinds` 说有几类，盘面就得链得到
  几类」「断言直接扫目录而不是照清单拼」）。

#### 🔴 `tier` 与 `sparse` 必须进 Spec，不能只写在文档里

`因子实现规格.md` 里那四档可信度与 7 个稀疏字段，**只写在 md 里等于没写**
（同「靠人记得跑的步骤 = 迟早不跑」）。它们要跟着因子值一路走到页面上：

    ✅✅ exact  实测定案（与聚宽/外部源逐位对过）
    ✅  std     标准公式（业界通行，本地无对标）
    ⚠️  own     **自建定义** —— 名字来自清单，口径是我们自己定的
    ❌  n/a     不实现（那 4 个，注册表里根本没有）

🔴 **⚠️ 那 42 个是这个模块最大的误用风险**：它们的名字与聚宽那份清单一字不差，
而口径是自建的。不标的话，拿本模块的 IC 去跟 `factors.xlsx` 的 IC 比就是
**在比两个不同的量**，而它不报错（同「对不上券商软件时，人会以为是数据错了，
而不会想到是口径不同」）。

### 3.2b 表达式因子：一个字符串就是一个因子（`factors/expr.py`）

```python
E = 'rsum(where(R>0,V,0),20)/rsum(V,20)'
Spec('vup20', '20日涨日成交量占比', 'vol',
     E,                                   # <- 公式（给人读）
     '…', '小数(0~1)', deps_of(E), warm_of(E),
     expr(E))                             # <- 实现（同一个字符串）
```

**这一层初版设计里没有**，它填的是「想到一个公式」与「写进族文件」之间那一步：
在此之前试一个想法只能改 .py 再整库重建 142 秒，试错一轮的成本压过了想法本身。
现在全历史 1632 万行 **5~6 秒**出体检报告。

🔴 **求值器只有这一份，`factor_try` 与 Spec 都 import 它** —— 两边各写一个的话
「试的时候是这个数、进面板变成另一个」迟早发生，**而两边都不报错**。
★ 副产品：用 `expr()` 写的因子，`formula` 字段与 `calc` 是**同一个字符串**，
  公式与实现在结构上分叉不了（同「每档只存你填的那个，另一个永远现算」）。

`--selftest` 三条（300 只票全历史 148 万行）：

    ① 表达式复现 bias20        不等 0        求值器与族文件手写的 calc 同口径
    ② Spec 与试跑同一条路       不等 0        expr() 注册后与直接试跑逐位相同
    ③ 反向自证（×1.000001）    不等 148 万   判据抓得住，前两条不是空转

全量那次也验过：16,321,172 行、不等 0 个。

★ `deps_of` 走 ast 把派生列映射回**面板原始列**（`_tp` -> high/low/close/factor）
  —— 手写漏一列的表现是 `Ctx` 建派生列时静默跳过、那个因子整列为空，**不报错**。
⚠ `warm_of` 只是**建议**：递推类真正要的远大于 n（本族约定 n×4，
  另有 120 根下限），要自己再想一遍（同「段落取自源码里的标记，是排版不是语义保证」）。

#### 🔴 报告里必带「是不是已经有了」

与现有因子的**秩相关**（不用皮尔逊：因子拿去做横截面排序，重要的是序不是标度；
量纲差几个数量级时皮尔逊会被极值主导）。实测复现式的写法立刻显出 |r| = 1.000，
而真正的新想法（双均线比）最高 0.814。

`--dups` 把这件事对**已在面板里的**也问一遍 —— 98 个因子 4753 对里
**33 对 |秩相关| ≥ 0.999**，好几对是**代数恒等**的：

    price_div_ma20 与 bias20     (C−M)/M ≡ C/M−1
    to_ma20        与 to_sum20   Σ₂₀TO ≡ 20×MA(TO,20)
    var20          与 std20      var ≡ std²（序相同）

它们在 `factors.xlsx` 里是**不同的行** —— 所以那 285 个名字背后的
**独立因子数远没有那么多**。★ 不因此删：秩相同 ≠ 值相同，
而且原清单本来就是两行；这里只负责让重复看得见。

#### 🔴 刻意【没有】「只跑最近 N 年」

第一版有 `--years`，理由是"调试快"。而截断历史会让长窗口因子在起点附近算出
**与面板不同的值** —— 试的时候看到一个分布、进面板变成另一个，**不报错**。
实测全历史只要 5 秒，那个选项纯粹是陷阱，删掉（同「刻意删掉那个
『这个率含不含规费』开关 —— 它是最容易填错的一处」）。

#### ⚠ 受限 `eval` 与 `query.py` 的三层防护**不是一回事**

`query.py` 防的是"从看板上把 `mart/` 写坏"（语句白名单 + 关键字黑名单 +
子进程超时）。这里输入来自族文件字面量或自己的键盘，命名空间限制只为了
**手滑时报错指得到原因**（写错列名当场列出有哪些），不是安全边界。
**别把两者的分工记反。**

#### 🔴 `warm` 要有**下限**，不只是"按需要取"

`indicators.py` 那条：

> 预热有个**下限 120 根**而不只是"按需要取"：RSI/ATR 这类 Wilder 递推
> **永远记着起点**，多喂 24 根末尾的值就会差几厘

因子模块里同样有 Wilder / EMA 族。**下限统一 120 根**，并且增量那条路
必须真的多读这 120 根 —— 少读不报错，只是那几天的值悄悄变了。

### 3.3 assay 侧

```
assay/assay/feed.py         + factors(date, names=None, codes=None, carry_days=0)
assay/assay/guard.py        + factors(...)  -> self._check_date(...)  🔴 一道都不能少
assay/assay/factor_eval.py  IC / rank IC / IR / 分位收益 / 换手（长表）
assay/srv/factors.py        /api/factors/defs   /api/factors/eval
assay/web/factors.html      因子广场（复用指标广场那一套形态）
```

**`feed.factors` 的签名与既有三个对齐**（判据 ③：同一套 as-of 与停牌语义）：

```python
def factors(self, date, names=None, codes=None, carry_days=0):
    """因子当日截面 -> DataFrame（第一列 jq_code）。

    names=None 取全部 persist 的因子。
    carry_days > 0 对停牌股 ASOF 结转 —— 🔴 只结转**价格派生**那几族
      （ma/osc/pos/dist），会计比率与 TTM 不结转（同 snapshot 那条：
      结转会拿到该股最后交易日那天的过期报告）。
    """
```

🔴 **必须走 `guard`**：前三个 API 的 PIT 检查各有一道，注释写着
「少一道防火墙就是给未来函数开了个后门，而它**不报错**，只是回测结果好得可疑」。
因子进策略之后，未来函数的风险面直接放大 200 倍。

🔴 **策略不许直接 `read_parquet` 因子面板** —— 那正是 froec/红利把 9 层 CTE
写进策略文件的老毛病（口径与规则混在同一段文本里）。selftest 钉一条。

### 3.4 因子广场 `/factors.html`

形态**照搬指标广场**（`/indicators.html`），不重新设计：
一卡一因子（短名 / 全名 / 族 / 单位 / desc / formula / **tier 徽标** /
**sparse 警告** / 一张真图）、分页、搜索匹配名称+说明+公式、
**整页照服务端那份清单渲染，页面里没有任何一个因子名**。

★ 它是**「🔄 数据」的子页**还是**回测域的子页**？——**回测域**：
因子是做策略时用的（同「指标广场是个股的子页」那条的判法：
看"什么时候会进这一页"，不是看"它像哪一类数据"）。

## 四、怎么落盘：**按【股票】分块，不按年**

    全量重建   142 秒 / 16,321,172 行 / 8.89 GB (float32) / 24 个年份文件
    行数与面板【逐年完全相同】

### 🔴🔴 初版设计说的是"分年批 + 预热"，那是错的 —— 自证当场打红

初版写「按年分区、每段往前多读 3 年当预热」。`--check`（重算一年与盘上逐位比）
报出三个根因，**都无法靠加预热解决**：

    ema120   757,753 / 1,233,202 行不等，max 相对差 4.8e-3（0.5%，不是噪声）
             -> EMA 递推**永远记着起点**，480 根预热只把种子权重压到 3.7e-4
    ma5/ma10 2014 年 6 / 11 个不等，恰好 n+1 的形状
             -> **长期停牌股**复牌时窗口跨过几年缺口，预热给多少都不够
    skew20   ~1e-7 相对差 -> pandas 的 rolling 是**在线算法**，本身就依赖起点

也就是「同一年的值取决于它在哪一段里被算的」= **不可复现**，
而它不报错（落盘、行数、非空率全正常）。

**改成按股票分块，预热这个概念从根上消失** —— 98 个因子全是逐股算的，
每块取该股**全历史**，块怎么切结果都一样。
🔴 自证：**块 700 -> 233 重算 2026 年，913,200 行 × 98 列逐位一致**。
🔴 加**横截面因子**时不能直接塞进来（会被切碎且不报错）—— 启动时有断言钉住。
★ 顺带更快：142s vs 分年段的 188s（不再重复读预热年）。

### 每天全量重建，不做增量

做"只算最后一天"要为递推类因子存中间状态 = 第二份实现，
**省三分钟不值得拿逐位可复现去换**。

### `_meta.json` 记两个指纹，少一个都会让"过期"变得看不见

| | 变了意味着 |
|---|---|
| `panel` | 面板被修正过（本项目修过 volume 7.5 万行 / 复权因子 / ETF 价格刻度）|
| `specs` | **公式改了** —— 盘上的值按旧公式算，而它长得和新的一模一样 |

第二个尤其重要：改一行 `calc` 不报任何错，只让 `mart/` 里那 8.9 GB 悄悄过期。
指纹都没变就秒退。

### 🔴 归档指纹不受影响（这是最大的风险，已核实）

`feed.PanelFeed.FINGERPRINT_PARTS` 三个 glob 对本模块 26 个产出文件
**命中 0 个** —— 历史归档的 `data_fingerprint` 一个字节都不会变，
去重判据 / 模拟盘对账 / tick 的「指纹没变就跳过」全都不受影响。
★ 这是「`PANEL_GLOB` 必须是平的（不许 `**`）」那条守卫的直接红利。
🔴 **反过来说：因子面板绝不能落进 `mart/panel_daily/`** —— 那会让全部历史
  归档的指纹当场作废。

### 落盘的两条纪律

- **整目录原子替换**（tmp -> rename）：逐个文件换的话中途失败会留下
  半新半旧的一批年份，而那不报错，只是有些年是新公式、有些是旧的。
- 要读哪几列取自各 Spec 的 `deps` **并集**，不写死 —— 写死的话加一个用到
  新列的因子会静默读不到（更糟的是某些路径下拿到全 NaN）。

### 🔴 评价层用**长表**不用宽表 —— 58×

实测同一份数据：宽表 `733.6 s/年`，UNPIVOT 成长表 `12.6 s/年`。
这不是优化技巧，是**这一层能不能每天跑**的分界。

### 🔴 评价序列天然滞后 20 个交易日

IC 要 `fwd20`（未来 20 日收益），所以**今天 09-23 只能结算到 08-25**。
页面必须把这句话写出来 —— 否则人看到"最新 08-25"会以为链条坏了
（同「数据日与报价时间写在同一个标签里」）。

## 五、接进 `sync_daily.sh`：**链尾，10/10**

现状（实测读的）：

```
1/9 tdx2db cron   2/9 PIT 快照   3/9 ETF 价格重写   4/9 更新体检
  ├─ 体检失败 -> 5~8 整体跳过（不在坏数据上继续加工）
5/9 load_tdx_kline && 6/9 交易日历 && 7/9 面板（本年增量） && 8/9 beta
9/9 ETF lake                                  ← 链尾，失败不影响主面板
```

新增 **`10/10 因子面板`**，**排在 8/9 之后**（它吃 7/9 的产物 `mart/panel_daily`），
与 9/9 并列在链尾：

```bash
run "10/10 因子面板（策略与因子广场吃它）" "$ROOT" \
    python3 datalake/build/build_factor_daily.py --year "$(date +%Y)"
```

★ 放链尾的理由与 9/9 **一字不差**：它失败不影响主面板，而主面板才是
  `is_stale` 的判据 —— 所以不会因为它失败就每 10 分钟重跑整条链。
★ 判据落在**顺序**上（`build_panel_daily` 必须在它之前），不是"提到过这个名字"
  —— 挪到前面它读的是**昨天**的面板，**而那不报错**（同 9/9 那两条变异）。
⚠ **评价层不进 `sync_daily.sh`** —— 它属 assay，而且滞后 20 天、低频。
  挂 `tick_daily.py` 或手动跑，见第八节分期。

## 六、🔴 三条必须【先定】的口径

不定的话模块建起来也是错的，而且改一次评价序列整份作废（246 秒重跑）。
下面给**建议值 + 理由**，请确认或改：

| | 建议 | 理由 | 代价 |
|---|---|---|---|
| **前瞻窗口** | `fwd1 / fwd5 / fwd20` **三个都算** | 一次算三个只多 ~15% 时间，而"这个因子适合什么频率"本来就是要回答的问题 | 评价序列滞后按**最长**那个算（20 日） |
| **股票池** | 剔 ST / 停牌 / **上市不满 120 日** | 与 `market.TRADEABLE` 同源（`public_status IN ('正常上市','ST','*ST')` 那条判据的**一处定义**）；次新股在小市值端会主导分位 | 与 `factors.xlsx` 的池子**大概率不同** -> IC 数值不可直接比（要写在页面上） |
| **无风险利率** | `r_f = 0` | 本地**没有** r_f 序列，编一个就是造数（同「不给点位，等权组合没有点位这回事」） | 3 个夏普类因子标 ⚠️ own，页面注明 |

**2026-09-23 状态：三条都还没定**，而它们各自卡着一件事 ——

| | 卡着什么 | 什么时候必须定 |
|---|---|---|
| 前瞻窗口 | 评价序列算不出来（IC 对着哪个收益、滞后几天） | **第三期开工前** |
| 股票池 | 横截面分位切点、IC 的样本 | 同上 |
| `r_f` | 3 个夏普因子做不了 | 补完量价剩下那 4 条时 |

★ 前两条会被第三期**逼着定**，那正是把它排在前面的理由之一 ——
  口径定不下来的话，评价层做出来也只是一台生产不可比数字的机器。

🔴 **股票池那条要与 `market.TRADEABLE` 共用一处定义** —— 分两处写就会出现
「榜上 25 只、成分表 26 只」那种自洽的谎（实测踩过）。

## 七、守卫：这个模块建起来的同时要钉的判据

| 钉什么 | 为什么（都是"不报错"的坏法） |
|---|---|
| **因子数取注册表**，不写死 | 加一个因子广场上自动就有；写死清单的话新因子静默不出现 |
| **跨进程可复现**：同一天同一份数据，指纹逐位相同，**4 个进程比** | `PYTHONHASHSEED` 那轮：注册表迭代顺序不许依赖 `set`；同进程连跑只证明进程内可复现 |
| **`feed.factors` 必须走 `guard`**（ast 钉） | 少一道 PIT 防火墙 = 未来函数后门，而它只让回测结果"好得可疑" |
| **策略文件里不许 `read_parquet` 因子面板**（ast 钉） | 口径与规则混在一起，froec 那 9 层 CTE 的老毛病 |
| **`sparse` 与 `tier` 真的渲染到页面上**（渲染后可见文本） | 只写在 md 里等于没写；⚠️own 不标就会被当成"复现了聚宽那个因子" |
| **`build_panel_daily` 必须排在因子步之前**（顺序，不是"提到过"） | 挪到前面读的是昨天的面板 |
| **float32 + 分年批**（量峰值内存，不是查那个字面量） | 26.1 GB > 24 GB，表现是换页把 92 秒拖成 252 秒 |
| **等价性**：改口径前后逐位比指纹 | 与 `symbols.py` 66 项 / `live.py` 54 项同一套做法 |
| **selftest 不许写生产 mart** | 重定向到临时目录，跑完 `git status` 必须干净（同 `lv.LIVE` / `ASSAY_RUNS` / `MARKS_FILE` 三条） |

**已钉的（2026-09-23）**：

| 在哪 | 钉了什么 |
|---|---|
| `Spec.__init__` | formula/desc/unit/note/name_cn 里**不许有 markdown 星号**（它们会进目录表、接口、页面 title 属性；实测拦住过新写的 turn.py 9 处） |
| `register` | 因子**编号撞车响亮失败**（静默覆盖的话后注册的顶掉前一个，而目录表照样列得整整齐齐） |
| `build_factor_daily` 启动 | **没有横截面因子**（有的话会被按股票分块切碎，不报错） |
| `build_factor_daily --check` | **换块大小重算，逐位一致** |
| `factor_try --selftest` | 试跑 == Spec == 族文件手写，三者同一条路 + 反向自证 |
| `tools/check_vs_indicators.py` | 与 `assay/indicators.py` **25 项逐值对数**（相对误差 < 1e-10）+ 反向自证 |
| `build_factor_catalog` | 98/98 对回 `factors.xlsx` 行号（抓到过一个我打错的名字） |

⚠ 还没钉的：**跨进程可复现**（注册表迭代顺序不许依赖 `set`）、
  **策略文件里不许 `read_parquet` 因子面板** —— 前者要等 selftest 框架，
  后者要等第二期（现在还没有策略会用它）。

★ **每条守卫都要做变异测试**，且出现"漏了"先问**这个变异是不是无效的**
  （同 `roed` 那条）。

## 九、明确**不做**的三件事（记在这里，免得下次当成"漏了"）

| 不做 | 为什么 |
|---|---|
| **不改 `build_jqfactor_q.py` / `build_beta_daily.py`** | 它们是在用的（红利策略 / 基准 beta）。新模块可以**读**它们的产物，但不去"统一"—— 那会改变现有策略的历史归档（同「没有去修 froec.py 的排序」） |
| **不把 `factors.xlsx` 的 IC 当基线对数** | 那份数据的股票池 / 持有期 / 超额口径全未知，逐位对不上是**必然**的。能做的只有**方向自证**（tr20 负 IC、低换手溢价 —— 已验过方向一致） |
| **不做"因子自动挖掘/组合优化"** | 那是另一个问题域。本模块只回答「有哪些因子、值是多少、在本地数据上表现如何」；怎么用是策略的事（判据 ④） |
